## 第一部分：必填章节核对表（结构一览 + 强约束）

> ⚠️ **结构强约束（v10.1）**：产出 plan 后**逐节核对下表**——缺章节 = 未完成。**两种结构二选一**（在 §0 或变更记录注明选了哪种）：
> - **结构 A（复杂模块，默认推荐）**：`§2 模块拆分` 独立成节，T1-Tn 每个子任务独立小节（七要素）——多链路/多子任务模块必用（module-004 即此结构）。
> - **结构 B（简单模块）**：可精简（需求+方案合并），**但必须在 §0 或变更记录写明「为什么不需要模块拆分」**（如 <100 行、单文件改动）——写不清理由就按结构 A。
> ⚠️ **不就近参考同专项旧模块结构**（如 perm-003 的「需求+技术方案主题分区」即结构 B 未说明的变体，非权威）——以本表为准。

```
specs/module-XXX/plan.md —— 结构 A 完整骨架（module-004 同款）
├── # 开发计划 — Module-XXX: <名称>
├── ## 0. Agent 配置清单    [必填] ← 角色实例 + 审查要点 + 拆解理由 + 结构 A/B 声明
├── ## 1. 需求描述          [必填] ← 需求来源 + 用户故事/BDD + 关键约束（不变量）
├── ## 2. 模块拆分          [结构 A 必填] ← 子任务 1~N，每个独立小节含七要素（描述[现状→修法→理由+行号]/预估/文件/依赖/子验收）
├── ## 3. 技术方案          [必填] ← 全量实证盘点 + 数据表/SQL + API 变更 + 外部依赖 + 关键改动点汇总
├── ## 4. 验收标准          [必填] ← 引用 acceptance-criteria.md + 可运行验证命令
├── ## 5. 风险评估          [必填] ← 每条风险含具体应对
├── ## 6. 变更记录          [必填] ← 版本/日期/变更内容/变更人
└── ## 7. 审批记录          [必填] ← Planner/用户审批/Developer/Reviewer/Tester 状态（用户行由 Developer 入场回填）
```

**核对要点**：
- §0 是否声明结构 A/B？结构 B 是否写明精简理由？
- 结构 A：§2 是否 T1-Tn **独立小节**（不是一段话带过）？每个子任务是否七要素齐？
- §1 不变量是否编号列明（防回归）？

## 第二部分：详细规格

### §0 Agent 配置清单
- **角色实例**：如 `Planner×1 + Developer×1 + Reviewer×1 + Tester×1`；全栈模块可写 Developer-Frontend + Developer-Backend。
- **审查要点（Reviewer 须核什么）**：列出 Reviewer 审查时必须核对的不变量/关键点（如「前端 401 语义」「业务角色矩阵不变」「白名单只减不增」）——让 Reviewer 有明确核对对象。
- **拆解理由**：为什么这样拆（依赖关系 / 可并行性 / 风险隔离）。

### §1 需求描述
- **需求来源**：哪个文档哪一节（如 `docs/功能说明.md §X`）。
- **用户故事**：`作为XX，我想要XX，以便XX`。
- **验收场景（BDD）**：Given/When/Then 列举关键场景。
- **关键约束（不变量）**：编号列明本次开发不得破坏的既有约定。**这是 module-004 样板的核心差异点**——写清不变量可防止改出回归（如「登录失败返回 400 非 401，LoginView 依赖」「现有角色矩阵不新增规则」）。
- **不变量合法性检查（v10.2）**：凡声称「某文件零改动/不动」的不变量，必须先实际检查该文件（grep/读代码）确认既有约束（URL 级权限、注解、拦截器、角色白名单等）不会挡本模块功能——防「计划假设与代码现实冲突」（脱敏教训：声称安全配置零改动，但既有 URL 级权限锁死目标接口，开发中途被迫改）。

### §2 模块拆分（每个子任务独立小节，含七要素）
1. **描述**：现状 → 修法 → 理由，**行号级引用**具体代码位置（如 `SecurityConfig.java L120-135`）——禁止只写「实现 XX 功能」。
2. **预估代码量**（默认 ≤200 行/模块，超了在本节说明理由）。
3. **涉及文件**：新增/修改文件清单。
4. **依赖**：上游子任务/已完成模块。
5. **子验收**：本子任务的完成标准（可验证）。
6. 状态（可选）：📋 待开发 / ✅ 完成。
7. 测试策略（可选）：本子任务如何测。

> 🎯 **lead 风格示例（脱敏自 module-004 T1，对齐颗粒度基准）**——子任务描述必须写到这个细度：
> ```
> ### 子任务 1（T1）: <缺陷/功能名>（<一句话定位>）
> - 描述:
>   - `XxxServiceImpl.login` 现用 `if (!request.getPassword().equals(user.getPassword()))`（L111），而 `XxxController.login` 先 `request.setPassword(encode(request.getPassword()))`（固定盐确定性 hash）再比较字符串。该机制仅对「固定盐 hash」种子生效，其余随机盐/损坏 hash 种子无法登录。
>   - 修法（两步，缺一不可）：
>     1. `XxxController.login`：**删除** `request.setPassword(encode(request.getPassword()));`（L59），向 service 传**明文**密码。理由：`matches(rawPassword, storedHash)` 期望第一个参数是明文。
>     2. `XxxServiceImpl.login`：改为 `if (!matches(request.getPassword(), user.getPassword()))`，并加入对应 import。其余登录逻辑（状态检查/失败计数/审计日志）**不动**。
>   - **同类缺陷一并修复**：`changePassword` 现用 `oldPassword.equals(user.getPassword())`（L524），同属该缺陷模式，一并收敛（同上两步）。
>   - 不修 register：`register` 的 `encode` 用于**存储**（合法），无需改。不新增防御逻辑（避免过度工程）。
> - 预估代码量: 生产代码 ~5 行（净删 2 行 + 改 2 处 + 加 import）
> - 涉及文件:
>   - `backend/src/main/java/com/platform/service/impl/XxxServiceImpl.java`
>   - `backend/src/main/java/com/platform/controller/XxxController.java`
> - 依赖: 无（独立）
> - 验收: 全部种子账号可用密码登录成功；密码错误仍返回业务码 400；changePassword 旧密码校验用明文 matches 生效。
> ```
> **自检**：写完每个子任务后对照——①有没有行号级引用？②现状/修法/理由三段是否齐？③「类似任务 N」式偷懒？④预估行数可核？

### §3 技术方案
- **3.1 全量实证盘点**：真实盘点现状（如「23 个 Controller、115 个端点映射矩阵」），禁止臆测、禁止凭印象写。
- **3.2 涉及数据表 / SQL**：DDL 迁移号（增量脚本 `sql/V<编号>__*.sql`）、幂等性（information_schema 判断）。
- **存储宽度约束检查（v10.2）**：新增枚举值/编码（岗位码/状态码/权限码等）前，确认目标存储/介质的长度约束（DB 列宽、字段定义、协议规格等），防超长被静默截断或写入失败——适用于有持久化/结构化存储的项目；无存储项目（纯内存/嵌入式）可跳过（on/off）。
- **3.3 API 变更**：相对现状的端点新增/修改、参数、响应。
- **权限白名单双处对齐（v10.2）**：调整后端访问权限（URL 级权限/接口角色）时，同步核对前端路由/菜单的角色白名单（路由守卫、菜单显隐），防「后端放开、前端仍拦」或反之——前后端权限白名单双处维护要对齐。
- **3.4 外部依赖**：DB/Redis/第三方服务。
- **3.5 关键改动点汇总表**：`改动点 → 文件 → 影响`。

### §4 验收标准
- 引用同目录 `acceptance-criteria.md`（不重复抄内容）。
- **验证命令**：可运行的具体命令（`mvn test` / `npm run build` / curl 示例），Tester 照此执行。

### §5 风险评估
- 每条风险 = 风险描述 + **具体应对**（不是空话。如「Excel 数值型截断 → 模板文本格式 + 字符串解析」）。

### 禁止占位符（plan 质量红线，借鉴 writing-plans）
以下都是**计划缺陷**，绝不要写进 plan：
- 「待定」「TODO」「后续实现」「补充细节」
- 「添加适当的错误处理」/「添加验证」/「处理边界情况」（无具体做法）
- 「为上述代码编写测试」（没有实际测试代码）
- 「类似任务 N」（重复代码——工程师可能不按顺序读）
- 只描述做什么不展示怎么做（代码步骤必须有代码块/具体位置）
- 引用了未在任何任务中定义的类型/函数/方法
- 子任务描述只写「实现 XX 功能」（必须现状 → 修法 → 理由 + 行号级引用）

### 产出后自检三查（plan 完成标准，仿 writing-plans 自检）
写完整份 plan 后，以全新视角检查（发现问题直接内联修复，修好继续）：
0. **结构核对（v10.1，最优先）**：逐节对照「第一部分：必填章节核对表」——①§0 是否声明结构 A/B（结构 B 是否写明精简理由）②结构 A 时 §2 是否 T1-Tn **独立小节**且七要素齐（描述[现状→修法→理由+行号]/预估/文件/依赖/子验收）③是否缺任何必填章节（§0/§1/§3/§4/§5/§6/§7）——缺章节立即补
1. **规格覆盖度**：plan 的每条需求/不变量，都能指出实现它的子任务？列出所有遗漏并补
2. **占位符扫描**：搜索上方「禁止占位符」黑名单中的任何模式，逐个修复
3. **一致性检查**：跨子任务使用的类型/方法名/端点名是否一致（任务 3 叫 `clearLayers()` 任务 7 叫 `clearFullLayers()` 就是 bug）；编号（模块号/迁移号）无冲突
