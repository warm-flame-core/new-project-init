# docs/已知坑/ 文件夹模板（模板 34）
> 🗂️ **产出模式**：多次创建-含文件夹（复制整个 `已知坑/` 文件夹结构新建；目录内的**单篇**由 `_模板.md` 复制新建）；模板目录：templates/多次-含文件夹/（v11.4 新增）
> 📍 **变更记录方向**：新行追加底部（有人看；见 SKILL.md 文档维护规则第 9 条）
> 🧩 **产出物路径**：`docs/已知坑/`（`README.md` + `_模板.md` + `NNNN-<短标题>.md` …）
> ✅ **适用条件**：所有场景（全新 / 中途 / 存量）。存量项目初始化时把三处旧踩坑落点搬入（从 `0001` 起编号）；全新项目先建 `README.md` + `_模板.md` 骨架，首次踩坑再补单篇。
> 🔀 **on/off 说明**：本目录**默认产出**——`<入口规范文件>`（AGENTS.md / CLAUDE.md）路由表有一行指向它，不建即死链。只有用户明确要求「本项目不记录踩坑」时才整目录跳过，**跳过时必须同步删掉路由表那一行**并在收尾说明。目录内三文件：`README.md`、`_模板.md` 必产；单篇按需增（**0 篇也合法**，索引表保留表头）。
> 📎 **定位**：项目踩坑的**唯一出处**。把「现象 → 根因 → 固定解法」从散落各处（入口规范文件 A4 环境速查 / 部署文档「已知坑」节 / tools README「使用注意」）收敛成「**索引 + 单篇**」两层——索引常读且短，单篇按需展开且可写很细。

> ⚠️ **维护声明**：本文档修改后必须在末尾「变更记录」表追加一行——`YYYY-MM-DD HH:mm | 变更内容 | 署名`（署名按四段式 实体人-平台-角色@分支（无 git 省略 @分支，如 warmflame-Reasonix-Developer@feat/xxx）；无法确认身份先问用户）。
> 本模板**语言无关**：示例均为脱敏通用例子（不出现具体项目名 / 私有地址 / 真实凭据 / 内网信息）。

## 第一部分：结构一览

```
docs/已知坑/（产出物：整目录一次建齐）
├── README.md          ← 唯一入口：三条限定语 + 规则速查表 + 全部坑索引 +（可选）已失效/误报条目
├── _模板.md           ← 新建单篇时**复制这个**（复制完不改 `_模板.md` 本体）
└── 0001-<短标题>.md    ← 单篇：现象 / 排查过程 / 根因 / 固定解法 / 如何验证已规避 / 提炼规则

README.md 章节结构（索引层；按需加载，体量硬门禁 1-3 KB）
├── 定位一句话
├── 三条限定语        ← ①只记已发生的坑 ②先读索引再决定展开哪一篇 ③每条规则都链到唯一出处
├── ## 规则速查表     ← | 规则（祈使句） | 触发场景 | 详细复盘 |
├── ## 全部坑索引     ← | # | 标题 | 发现日期 | 模块 | 状态 |
└── ##（可选）已失效 / 误报条目

NNNN-<短标题>.md 章节结构（单篇；不设字数上限）
├── # NNNN <短标题>
├── 发现日期 / 模块 / 状态          ← 头部三字段单行
├── ## 现象                        ← 怎么发现的、原始报错
├── ## 排查过程                    ← 试过什么、为什么排除
├── ## 根因                        ← 机制级，不是「那行代码写错了」
├── ## 固定解法                    ← 可复制粘贴的命令 / 代码
├── ## 如何验证已规避               ← ★ 落成可检查的东西（测试/脚本/规则/门禁）
└── ## 提炼规则                    ← 一句话祈使句 → 会被 README 速查表收录
```

**两层分工（为什么不是一个大文件）**

| 文件 | 谁读 | 何时读 | 体量 |
|------|------|--------|------|
| `README.md` | 人 + AI | 遇到报错 / 环境问题 / 模块收尾回看时**第一站** | **1-3 KB 硬门禁**（它是按需加载的入口） |
| `NNNN-*.md` 单篇 | 人 + AI | 只有 README 命中（索引或速查表指到它）时才展开 | 不设上限，复杂坑写详细 |
| `_模板.md` | AI | 新建单篇时复制成 `NNNN-*.md` | 空骨架 + 每节写作提示，**不填真实内容** |

> 🛑 **体量红线**：README 超过 3 KB = 写歪了（速查表写成了复盘、或索引里塞了细节）。修法是把细节下移到单篇，README 只留一行。README 变长不会让人更容易找到坑，只会让人更不愿意读。

## 第二部分：详细规格 + 示例片段

### 1. 产出物分工与文件命名

- **`docs/已知坑/`** 整目录一次性建齐（三个文件的分工见上方表）；后续新增 = **只复制 `_模板.md`** 新建单篇，不动目录结构。
- **单篇文件命名**：`NNNN-<短标题>.md`
  - `NNNN`：四位十进制，从 `0001` 起**顺序递增，不复用已删编号**（索引里 `#` 列 = 该编号，不带 `.md`）。删号复用会让历史引用指错篇。
  - `<短标题>`：中文短横线连接的短句，读到就知道坑是什么（如 `0007-权限白名单三处未同步.md`）；**不要**写 `0007-问题记录.md` 这类无信息标题。
- **编号与模块解耦**：编号是全目录流水号，不按模块分段（模块列在索引里，不进文件名）。
- **并行场景取号（装配 30/31 时）**：多个 agent 并行工作时，**编号由主 agent（或唯一写者）统一分配**后再落笔——各自「看索引取最大号 +1」会撞号（撞号 = 两篇同号、索引链接指错）。

### 2. `README.md` 逐节规格

#### 2.1 三条限定语（必写，逐字保留语义）

````markdown
> ⚠️ **读之前先知道三件事**：
> ① 这里只记**已经发生过**的坑——不是预想的风险（预想风险在 plan §5 风险评估 / 演进清单）。
> ② **先读完本索引再决定展开哪一篇**，不要一次把所有单篇全读（索引就是为此存在的）。
> ③ 每条规则都链到**唯一出处**（某篇单篇的「提炼规则」节），不在本文件里复制正文。
````

> 三条限定语是防退化的机制，不是客套话：①防「把风险清单塞进来」导致索引失信；②防「AI 一次读完全部单篇」白烧上下文；③防「索引里再写一份复盘」造成双份漂移。

#### 2.2 规则速查表（本文件的**主表**）

````markdown
## 规则速查表

| 规则（祈使句） | 触发场景 | 详细复盘 |
|----------------|----------|----------|
| 改权限必须三处全量对齐（URL 级 / Service 层矩阵 / 前端白名单），只改一处等于没改 | 新增角色、放开接口权限、菜单加可见性 | [0007](0007-权限白名单三处未同步.md) |
| 脚本里不写中文字面量（中文写临时文件再读） | 写任何会被非 UTF-8 环境执行的脚本 | [0001](0001-脚本中文在-Windows-下失败.md) |
````

- **一行 = 一条会再犯的模式**；规则必须写成**祈使句**（「必须 / 不要 / 先…再…」），不写名词短语。反例：`权限白名单问题`（名词，不可执行）。
- 一篇单篇可提炼**多条**规则 → 多行，`详细复盘` 列都指向同一篇（这是允许且鼓励的：一条坑往往对应多个触发场景）。
- `详细复盘` 列：**相对链接**（`NNNN-xxx.md`，站内可跳），链接文字用编号；同一规则有多个出处时**只能有一个**（唯一出处原则）。
- **新增规则只往下追加**，不重排既有行（行序稳定 = 老链接不断）。

#### 2.3 全部坑索引（全量台账）

````markdown
## 全部坑索引

| # | 标题 | 发现日期 | 模块 | 状态 |
|---|------|----------|------|------|
| 0001 | 脚本中文在 Windows 下执行失败 | 2026-08-14 | 环境 | 已规避 |
| 0007 | 权限白名单三处未同步 | 2026-09-03 | module-004 | 已解决 |
| 0012 | 缓存与库状态不一致导致偶发空数据 | 2026-09-21 | module-007 | 待观察 |
````

- **状态取值只有三个**（不得自造）：
  - `已解决`：根因已修，且有「如何验证已规避」的落点守住。
  - `已规避`：根因不便修（外部工具/平台行为），但已有固定解法绕开。
  - `待观察`：解法已上但未在真实场景复验，或同类现象可能还有残留。
- 上例仅示数行；真实索引按编号**连续**列全（缺号 = 单篇被删，需在「已失效/误报条目」说明去向）。
- **发现日期**：首次观察到的日期（`YYYY-MM-DD`），不是写单篇的日期；取不到确切日期就写月份并标注（如 `2026-09 上旬`）。
- **模块**：出现该坑的模块名/目录归属；环境级写 `环境`。
- 索引行与单篇头部三字段（发现日期 / 模块 / 状态）**必须一致**；改状态时两处同改。

#### 2.4 可选节：已失效 / 误报条目

````markdown
## 已失效 / 误报条目

| # | 原标题 | 结论 | 误判原因 |
|---|--------|------|----------|
| 0004 | 构建偶尔失败疑似缓存污染 | 误报 | 实为共享库瞬时不可达，与缓存无关 |
````

- 用途：曾经以为是坑、后来证明不是的，**保留在此**（删掉 = 下次还会重复排查）。
- 条目正文单篇可删（并在本表说明去向），也可保留但把状态改成失效说明；**不要静默消失**。

#### 2.5 变更记录豁免（显式声明）

- `README.md` **不设变更记录表**：索引行与速查表行本身就是变更证据，设表会挤爆 1-3 KB 体量门禁（对齐 SKILL.md 文档维护规则第 9 条「豁免无变更记录表文档」）。
- `_模板.md` 顶部写一行 `> 模板版本：v1（<日期>）`；**结构**变更时更新该行并追加一行简短说明（如 `v2：新增「如何验证已规避」四类落点表`）。单篇不做逐篇回改。

### 3. `_模板.md` 规格（新建单篇的复制源）

`_模板.md` = 单篇骨架 + 每节写作提示，用尖括号占位，**不填任何真实内容**；复制成 `NNNN-<短标题>.md` 后才填写。示例（可近乎照此）：

````markdown
# NNNN <短标题>

> 发现日期：<YYYY-MM-DD> ｜ 模块：<模块名或「环境」> ｜ 状态：<已解决 / 已规避 / 待观察>
> 新建本篇后，**必须**同步补 `README.md` 两行：①「全部坑索引」一行 ②「规则速查表」一行（见 README 顶部限定语③）。

## 现象

<怎么发现的：在哪个动作/哪条命令/哪个页面上暴露；原始报错原样粘贴（不要转述），有日志/截图给路径。>

## 排查过程

<按时间顺序：试过什么 → 结果 → 为什么排除。被证伪的假设也要写（后来者会先想到同一个假设）。>

## 根因

<机制级：为什么这个现象必然会这样发生。不是「某文件某行写错了」。
 判据：读完后能预测同类现象（换模块/换语言仍成立）。>

## 固定解法

<可复制粘贴的命令 / 代码块。语言无关处用占位符（<项目路径>、<角色码>）。
 涉及写操作、数据库、外部服务的命令必须标注前置条件与用户确认要求。>

## 如何验证已规避

<★ 落成可检查的东西，四类落点至少选一类并写出具体产物：
  ① 测试（断言/回归用例）② 脚本或门禁（能红/绿）③ 规则（写进入口规范文件/模板必填项）④ 检查清单（模板里的一条 checkbox）
  禁止只写「以后注意」。>

## 提炼规则

<一句话祈使句，会被 README 速查表收录。含触发场景（什么时候该想起这条）。>

<!-- 单篇不设字数上限：复杂坑就写详细；但「现象/根因/固定解法」三节必须自洽可独立读懂。 -->
````

### 4. 单篇逐节详细规格

| 节 | 写什么 | 禁止 / 常见写歪 |
|----|--------|----------------|
| `## 现象` | 怎么发现的（哪个动作、哪条命令）、**原始报错原文**、日志/截图路径 | 转述报错（「报了个编码错误」）；只写结论不写触发动作 |
| `## 排查过程` | 试过什么、结果如何、**为什么排除**；含被证伪的假设 | 只写最后一步（「发现是白名单问题」）——排查过程的价值在排除项 |
| `## 根因` | 机制级解释：谁与谁不一致 / 哪份副本没同步 / 哪种环境假设不成立 | 「某某文件第 N 行写错了」（代码级，换个模块就失效，不可预测） |
| `## 固定解法` | 可复制粘贴的命令 / 代码块 + 前置条件 + 写操作确认要求 | 只写思路（「重新生成配置即可」）；命令里硬编码个人机器路径 |
| `## 如何验证已规避` ★ | **落成可检查的东西**（见下方四类落点表） | 「以后注意」「下次记得」「写完再检查一下」——不可检查 = 未完成 |
| `## 提炼规则` | 一句话祈使句（祈使动词开头 + 触发场景） | 名词短语（「权限白名单」）；一句话里塞两件事 |

> **根因的「机制级」判据（好 / 坏对照，均为脱敏通用例）**
> - ❌ 坏：`XxxService` 第 88 行漏加新角色，所以拿不到数据。
> - ✅ 好：权限判定在 URL 级、Service 层、前端各存**一份独立维护的白名单副本**；「开放权限」这个动作在任何一处单独完成都只局部生效，其余副本会否决——只要**同一权限存在多份副本且无对齐检查**，就必然出现「看起来放开了却拿不到数据」。
> - 判据：读完好的根因，你能预测「另一个模块放开另一个端点」会不会再犯；读坏的根因，只能祈祷下次记得改那一行。

**「如何验证已规避」四类落点（至少落一类，写出具体产物名）**

| 落点 | 形式 | 脱敏示例 |
|------|------|----------|
| 测试 | 断言 / 回归用例 | 访问矩阵断言测试：角色 × 端点 → 期望状态码，任一不符即失败 |
| 脚本 / 门禁 | 一行命令，能红 / 绿（退出码可判） | 收尾脚本比对三处白名单条数一致，不一致退出码非 0 |
| 规则 | 写进 `<入口规范文件>` B 区硬规范、或写进 plan/acceptance 必填项 | 「改权限必须贴三处 grep 输出」写进硬规范 |
| 检查清单 | 模板里的一条 checkbox | plan §3 盘点矩阵未填 = 不能进开发 |

> ★ 这一节是本模板存在的理由：**没有可检查落点的坑记录，等价于「以后注意」**。若当下确实做不出落点（外部工具行为、无测试框架），则必须写明「为何做不出 + 人工复验步骤（谁、何时、跑什么、看什么）」，并把状态标为 `待观察`。

### 5. 准入判据（决定值不值得写一篇）

**三判据全中才写单篇**：

| 判据 | 满足的样子 | 不满足的样子 |
|------|-----------|-------------|
| **隐蔽** | 机制不明显，第一次遇到会先怀疑别的地方（排查过程 ≥2 个被排除的假设） | 报错直接把原因说出来了（如「端口被占用」「文件不存在」） |
| **系统性** | 逃逸原因是**流程 / 工具 / 约定缺口**——补上机制后同类问题不再出现 | 一次性手滑、拼写错误、单个文件漏改（改完就没事了） |
| **重犯代价高** | 消耗过真实调试时间（不是顺手一问），且**下次同样条件还会发生** | 只是好奇查了一下；或者只在一次性迁移里出现过 |

**分流表（不符合三判据的去哪）**：

| 这条记录的性质 | 落点 |
|----------------|------|
| 一次性笔误 / 单次手滑 | 模块 `changelog.md` 技术债务登记，**不进**本文件夹 |
| 预想的风险（还没发生） | plan §5 风险评估 / 演进清单，**不进**本文件夹（本文件夹只记已发生的） |
| 跨项目通用的坑（如控制台中文乱码） | 本文件夹单篇 **+** SKILL.md 记忆纪律第 8 条的全局记忆（作用域不同，不算双份） |
| 工具的用法 / 参数 | `tools/README.md` 工具文档；只有「反复出问题的行为」才进本文件夹 |
| 已发生 + 隐蔽 + 系统性 + 重犯代价高 | ✅ **本文件夹单篇** |

### 6. 关键机制（硬门禁，必须写进产出物）

#### 6.1 写入硬门禁：两件事绑成一步

> 🛑 **新建 `NNNN-<短标题>.md` 的同时，必须补 `README.md` 两行**——①「全部坑索引」加一行 ②「规则速查表」加该篇提炼的每条规则各一行。**没补索引不算写完**。
> **判据**：在 README 里能通过编号/标题检索到本篇（索引行），能通过本篇的一句话规则检索到它（速查表行）——两条都成立才算完成。

| 借口（听起来合理，实为违规） | 现实 |
|---|---|
| 「单篇写完了，索引下次一起补」 | 索引是唯一入口，没补 = 这篇对后来者不存在，**等于没写** |
| 「速查表先不写，等坑多了再统一整理」 | 速查表就是「会再犯的模式」清单；不写等于只留了台账，丢了防重犯价值 |
| 「同一篇提炼出三条规则太啰嗦，写一条概括的」 | 速查表按**触发场景**检索，一条概括 = 三个场景都检索不到 |
| 「这坑很简单，写在 changelog 里就行」 | 走准入判据（§5）：三判据全中却塞 changelog = 违规；不全中却建单篇 = 污染索引 |

**状态同步**：`待观察 → 已解决/已规避` 时改两处——README 索引行的 `状态` 列 + 单篇头部 `状态` 字段，两处必须一致。

#### 6.2 写入门禁的触发点

| 触发点 | 何时 | 动作 |
|--------|------|------|
| **模块收尾回看阶段（主入口）** | 模板 24 阶段 6「回看踩坑（编码 / 工具 / 框架行为）」 | 发现本模块已发生的坑 → 过准入判据 → 值得写就**当场**建单篇 + 补 README 两行；**不攒到「以后统一整理」** |
| 存量完善初始化 | 初始化时发现三处旧落点有历史踩坑 | 逐条过判据 → 搬入并编号（见 §7） |
| 同一问题第二次出现 | 任何时刻（SKILL.md 记忆纪律第 8 条：同一问题出现 2 次以上 → 判定是否沉淀） | 判定是否达到三判据 → 达标即建单篇 |
| 收尾回看无产出 | 阶段 6 回看后确实没有新坑 | logs 记一行「回看无新增坑」（防「忘了做」，与模板 24 阶段 6 一致） |

#### 6.3 读的门禁（入口规范文件路由表）

- `<入口规范文件>`（AGENTS.md / CLAUDE.md）路由表**必须有且只有一行**：

````markdown
| 场景 | 先读 |
|------|------|
| 遇到报错 / 环境问题 / 工具有异常行为 | `docs/已知坑/README.md`（索引），命中后再展开对应单篇 |
````

- 有了这一行，AI 在恰当时机（报错、环境异常、收尾回看）一定会看到入口并去读索引——**这是本机制「会被真正用上」的唯一保证**，不能省。
- **读的顺序硬规则**：先读 `README.md` 索引 → 按索引/速查表命中**按需展开**那一篇；**禁止一次读完全部单篇**（README 的限定语②就是为此写的）。
- 路由表只指 README，不直接指单篇（单篇编号会增长，直接指单篇 = 路由表要频繁改）。

#### 6.4 唯一出处（防双份漂移）

- 三处旧踩坑落点统一改为**一行引用**：「见 `docs/已知坑/README.md`」——原内容搬入单篇，旧处**不留表体副本**（留副本 = 两份必然漂移，且读者不知道该信哪份）。
- 旧落点保留的只有**非坑内容**：模板 01 A4 保留「常用命令」；模板 15 保留部署步骤与「排查顺序」方法论；模板 23 保留工具用法、参数、构建语言等工具文档内容。
- 跨项目通用的坑：本文件夹单篇（本项目作用域）**+** 全局记忆（跨项目作用域），两者作用域不同，不算双份。

### 8. 一篇完整单篇示例（脱敏通用例，结构可照此）

````markdown
# 0007 权限白名单三处未同步

> 发现日期：2026-09-03 ｜ 模块：module-004 ｜ 状态：已解决

## 现象

给新角色开放「审计日志」菜单后，用该角色账号登录：菜单可见，点进去列表空白，接口返回 403。
原始响应：`{"code":403,"message":"无访问权限"}`；后端日志无异常栈，只有一条权限拒绝记录。

## 排查过程

1. 先怀疑前端角色码拼写错误 → 对照枚举定义逐字核对，一致，排除。
2. 怀疑网关/路由层未放行 → 路由配置里该路径已放行，排除。
3. 在 Service 层打印实际参与判断的角色值 → 值正确，但走了「未在白名单 → 拒绝」分支——**命中**。
4. 按目标角色在仓库全量检索白名单判断 → 共 60+ 处需并，URL 级与前端已改，Service 层漏并约 30 个文件。
5. 另发现一类必须**不并**的判断：target 侧防御（如「管理员账号禁止被本操作封禁」）——这类并入会变成越权漏洞，与「操作者放行」必须分开判定。

## 根因

访问权限的判定分散在**三份独立维护的白名单副本**：①URL 级（安全配置/网关路由）②Service/Controller 层角色矩阵 ③前端路由守卫与菜单显隐。三者是三条各写各的清单，没有任何对齐检查。

**「开放权限」这个动作在三处任意一处完成，都会表现为局部生效**；缺任何一处，现象都是「菜单可见但拿不到数据/仍 403」——只要**同一权限存在多份副本且无对齐检查**，就一定会有漏并的一处，且漏在哪一处由改动者的检索范围随机决定。

## 固定解法

```bash
# 1) 三处全量盘点（按目标角色/权限码 grep，输出需人工逐条判定放行 or 防御）
rg -n "<ROLE_OR_PERMISSION_CODE>" <安全配置目录> <服务层目录> <前端目录>

# 2) 生成盘点矩阵（每条一行），再动手改
#    列：位置 | 文件:行号 | 现状判断 | 判定（放行 / target 侧防御，保持不变）
```

- 判定规则：**操作者放行**（新角色要能执行该操作）→ 并入；**target 侧防御**（禁止对本角色自身/管理员执行）→ 保持不变。
- 三处改完后**重跑一遍同样的 grep**，比对三处命中条数一致（见下节脚本）。
- 改权限类改动属写操作前置：盘点矩阵需展示给用户确认后再改。

## 如何验证已规避

① **测试**：新增访问矩阵断言测试——遍历 `角色 × 端点 → 期望状态码` 表，任一不符即失败（新增端点时必须同时加表行，缺行即失败）。
② **脚本/门禁**：收尾脚本对三处白名单按角色码计数，三处不一致时退出码非 0，CI/收尾检查直接红。
③ **检查清单**：plan §3 的权限盘点矩阵为必填项，未填不得进入开发。

## 提炼规则

- 改权限必须三处全量对齐（URL 级 / Service 层矩阵 / 前端白名单），只改一处等于没改——触发场景：新增角色、放开接口权限、菜单加可见性。
- 权限盘点必须区分「操作者放行」与「target 侧防御」，防御类判断不得并入新角色——触发场景：任何涉及封禁/删除/代操作的权限调整。
````
