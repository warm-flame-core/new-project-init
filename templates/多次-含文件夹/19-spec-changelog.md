### 关键设计说明（核心差异点）
- 每条设计决策 = **决策标题 + 决策内容 + 原因**（为什么这么选、替代方案为何不用）。
```
### 设计决策 1: <标题>
- 决策：…
- 原因：…（替代方案…被否，因…）
```

### 自测结果
- 表：构建/测试命令 → 结果（如 `mvn test` 100/100 BUILD SUCCESS）。
- 真实环境冒烟：连接的真实环境 + 覆盖路径 + 结果；冒烟数据清理情况。

### 技术债务登记
- 本模块引入或新发现的债务：编号、描述、影响、处理建议（如「vue-tsc 1.8↔TS 5.9 环境性失败」）。

### Developer 交付前自审（四维清单，写 changelog 前自查，借鉴 implementer-prompt）
以全新视角审查自己的工作，发现问题在汇报前修复：
- **完整性**：规格中的所有内容都实现了吗？需求/验收项有遗漏吗？边界情况处理了吗？
- **质量**：命名清晰准确（匹配事物做什么而非怎么做）？代码整洁可维护？符合 CLAUDE.md 编码规范？
- **纪律**：避免过度构建（YAGNI）？只构建了要求的内容？遵循了代码库已有模式？（未遵循的在设计决策里说明原因）
- **测试**：测试真正验证行为（非只 mock 行为）？回归全量绿？测试输出干净无噪声？
- 自审发现问题 → 修复后再写 changelog；自审结论在「自测结果」节体现。

## 关键设计说明
### 设计决策 1: TD-1 登录机制统一 `BCryptUtil.matches`
- 决策：登录/改密校验统一走 matches，兼容固定盐与随机盐 hash
- 原因：预编码 hash 直比在随机盐下必然失败；matches 是 bcrypt 标准校验方式

### 设计决策 2: TD-4 种子 hash 统一为实测精确值（禁止手写）
- 决策：种子 hash 用本机 Python bcrypt 实测值
- 原因：手写 hash 无法通过 matches 校验（此前种子 hash 无法登录的根因）
