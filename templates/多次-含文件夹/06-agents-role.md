# agents/<角色>.md 章节模板（模板 06）
> 🗂️ **产出模式**：多次创建-含文件夹（复制特化模板文件夹新建，如 specs/module-XXX/）；模板目录：templates/多次-含文件夹/（v10.0 目录规整）
> 📍 **变更记录方向**：新行追加底部（有人看；见 SKILL.md 文档维护规则第 9 条）

> ⚠️ **维护声明**：本文档修改后必须在相应记录处追加（plan §6 变更记录 / changelog 变更记录 / 复用记录等）——`YYYY-MM-DD HH:mm | 变更内容 | 署名`（署名按四段式 实体人-平台-角色@分支（无 git 省略 @分支）；无法确认身份先问用户）。
> **按需创建**（B1 选「多 agent 分工」**且用户要详尽角色文件**时逐角色产出——默认多 agent 时四角色职责由 CLAUDE.md C 区（签署矩阵）+ D 区（工作流引用）+ specs 模板（17-21 输出格式）承担，只有项目要「角色文件详尽到照着做不用猜」才建 agents/*.md；单人+agent 不建）。示例=结构示范，agents 按问询答案填充。
> 参考：本项目 agents/ 四角色文件（planner/developer/reviewer/tester）为实战样板——角色文件要详细到「照着做不用猜」的程度（含输出格式模板、协作协议、自检清单）。

## 第一部分：章节结构一览

```
agents/<角色>.md
├── # <角色>（中文名）
├── ## 1. 角色定位        ← 一句话定位 + 什么时候需要
├── ## 2. 核心职责        ← 编号列出职责（含上下文维护）
├── ## 3. 输入 / 输出规范 ← 输入来源 + 输出物 + 输出格式模板（引用 specs 模板 17-21，不复制）
├── ## 4. 约束规则        ← 编码/流程/修复/禁止行为
├── ## 5. 上报与状态      ← 何时停下上报 + 状态词（BLOCKED/ESCALATE）+ 上报格式
├── ## 6. 协作协议        ← 与各角色的交接契约（交接带什么/接收方第一件事）+ 冲突循环引用 + 跨平台子代理兜底（后台派发先读 references）
├── ## 7. 工作流程        ← 步骤化
└── ## 8. 质量自检清单    ← checkbox 自检（四角色完整清单，照着打勾）
```

## 第二部分：详细规格

- **角色定位**：一句话（如 Planner=「需求分析与模块拆解」）+ 触发条件。
- **核心职责**：编号列表（如 Planner：需求澄清/模块拆解/计划+验收/上下文维护/ADR）。
- **输入/输出规范**：输入（plan/代码/报告…）、输出物（plan.md、changelog.md…）、**输出格式模板**（直接给该角色产出文件的骨架，如 Developer 的 changelog 格式、Reviewer 的 review-report 格式——照此写；**输出格式引用 specs 模板 17-21，不重复抄**，守唯一出处）。
- **约束规则**：强制约束（遵循 CLAUDE.md 编码规范/模块 ≤200 行/自测必跑）+ 禁止行为（如 Reviewer 禁止只给结论不给位置、Developer 禁止未自测交接）。
- **上报与状态（借鉴「何时停下来」清单）**：
  - **何时停下上报**（满足任一即停，不硬做）：需求不清 / 方案冲突（多方案需架构决策）/ 依赖缺失 / 计划与实际代码不符 / 对方案正确性不确定 / 任务超出本模块范围
  - **状态词**：`BLOCKED`（无法继续）/ `UNBLOCKED`（解除）/ `ESCALATE`（重试上限升级，动作标签表）
  - **上报格式（现象 / 尝试 / 需要什么帮助）**：如「BLOCKED：迁移 V31 与 schema.sql 冲突，尝试回滚失败，需要 team-lead 裁决以哪个为准」
  - **禁止**：猜测硬做、默默绕过阻塞、把问题留到交接才说
- **协作协议（交接契约）**：与 Planner/Developer/Reviewer/Tester/team-lead 的交接协议——**交接带什么**（产出文档 + 状态 + 遗留项）、**接收方第一件事**（读什么核对什么，如 Developer 入场核对 plan 审批记录）；跨会话交接引用模板 25 交接文档（§1 签署状态清单必填）；**产出文档/签署处署名用四段式 `<实体人>-<平台>-<角色>@<分支>`（无 git 省略 `@分支`；如 warm-flame-core-Reasonix-Developer@feat/xxx），无法确认 agent 身份时先询问用户（组员自写 agents 尤其要确认）**。
  - **冲突循环引用（不复制，只引用）**：Reviewer 退回 Developer → 模板 24 阶段 3（实现缺陷退修 / 需求偏差先回用户）；Tester 发现超验收范围行为 → 模板 21 §5.5；签署责任矩阵 → CLAUDE.md C 区
  - **跨平台兜底：子代理上下文（v11.0 强制，接 SKILL.md「跨平台强门禁」）**：本角色若由**后台派发、不继承父上下文的子代理**执行（Reasonix `task`/`subagent`、DSH `subagent`，见 `platforms/<平台>/adaptation.md` 档位表），**入场必须先 `read` 对应场景的 `references/场景/<全新|中途|存量>-问询.md` 全文**（以及 SKILL.md 相关规则）再执行，禁止凭残缺上下文现编题目；若发现自己本会话**没有 SKILL.md / references 上下文、或流程被精简/题目缺失** → **停下上报父代理或提醒用户**，不硬做（与 SKILL.md「生成期异常处理」红线一致）。继承上下文的主代理（DSH `subagent_fork`/`workflow`、Reasonix `-c/--resume`）按 SKILL.md 强门禁正常执行即可。
- **工作流程**：步骤化（接收 → 处理 → 产出 → 交接）。
- **质量自检清单**：四角色完整清单（Planner/Developer/Reviewer/Tester）见下方「四角色完整自检清单」小节，产出前逐项核对（照着打勾）。

### 示例（结构示范，摘自本项目 agents/planner.md 骨架）
```markdown
# Planner（规划师）

## 1. 角色定位
需求分析与任务拆解：接收用户原始需求，澄清确认后拆为可独立开发模块，输出计划与验收标准。

## 2. 核心职责
1. 需求澄清与确认
2. 模块拆解（默认 ≤200 行/模块）
3. 开发计划制定（plan.md）
4. 验收标准定义（acceptance-criteria.md）
5. 共享记忆库维护（三件套状态流转）
6. ADR 记录（发现者撰写，Planner 审批）

## 3. 输入 / 输出规范
### 输入
- 用户原始需求、既有代码、需求文档
### 输出
- specs/module-XXX/plan.md、acceptance-criteria.md
### plan.md 输出格式
# 开发计划 — Module-XXX: <模块名称>
## 1. 需求描述（含关键约束不变量）
## 2. 模块拆分（子任务七要素）
## 3. 技术方案（全量实证盘点）
## 4. 验收标准
## 5. 风险评估
## 6. 变更记录

## 4. 约束规则
- 问不透不写：必须基于用户确认的需求产出计划
- 禁止行为：不允许臆测代码现状（必须真实盘点）

## 5. 协作协议
- 与 Developer：plan.md + acceptance 交付，待审批后编码
- 与 team-lead：阻塞问题立即汇报

## 6. 工作流程
需求 → 澄清 → 拆解 → plan+acceptance → 记忆库更新 → 交接 Developer

## 7. 质量自检清单
- [ ] 计划基于问询/实证，无臆测
- [ ] 子任务含七要素
- [ ] 记忆库三件套已更新
```

### 四角色完整自检清单（照着打勾，产出前逐项核对）

**Planner（plan/acceptance 产出前）**
- [ ] 需求已澄清（ask 多轮问透，用户逐项拍板）
- [ ] 候选方案已对比（2-3 种 + 优缺点 + 选定结论；plan 只写 1 种）
- [ ] 不变量已编号列明
- [ ] 全量实证盘点（行号级引用，无臆测）
- [ ] 子任务七要素齐全（描述/代码量/文件/依赖/子验收/状态/测试策略）
- [ ] 验收项可执行（Tester 能照此判断过/不过）
- [ ] 记忆库三件套 + logs 已更新

**Developer（changelog 产出前）**
- [ ] 编译通过（mvn compile / cmake --build / pio run）
- [ ] 自测通过（全量测试 + 不变量逐条自查）
- [ ] 生产代码新增 ≤200 行（超出已在 plan 说明理由）
- [ ] 无占位符残留（待定/TODO/类似任务 N）
- [ ] 设计决策记录（决策 + 原因 + 替代方案为何不用）
- [ ] `.tmp-xxx/` 临时文件已清理（方法先归纳进记忆）
- [ ] 记忆库三件套 + logs 已更新

**Reviewer（review-report 产出前）**
- [ ] 独立审查（非 Developer 自审）
- [ ] 问题三级分级（需求偏差/阻塞/建议）+ 结论先行
- [ ] 每问题含现象/位置/根因/修复示例（禁只给结论）
- [ ] 验收标准逐条核对表已填
- [ ] 实测验证记录（真实跑过的命令 + 结果）
- [ ] 需求偏差已标记【需求偏差】且未自行修复

**Tester（test-report/签署前）**
- [ ] 全量回归绿（不是只跑新增）
- [ ] 真实环境冒烟已跑（含 DB/外部依赖的模块必须真实 DB）
- [ ] 环境性失败已归因（不算真实回归）
- [ ] 验收标准逐条核对（acceptance §1/§2）
- [ ] 超验收范围行为已记入 §5.5（记录不隐藏）
- [ ] 数据清理记录（冒烟临时数据已恢复基线）
- [ ] 签署区已填（测试人/结论/日期，不留空）

**四角色通用 · 日期纪律（v10.0 新增，防日志/签署日期错误）**
- [ ] **写日志/写记忆库前先确认当天日期**（系统日期为准，不凭记忆/惯性沿用旧日期）
- [ ] **logs 细档新日期必须新建文件**（`memory/logs/<角色>/<当天日期>.md`），**禁止在旧日期文件追加**；跨天会话按当天拆分
- [ ] **正式文档变更记录/签署区日期 = 实际修改当天**（不滞后不预写）；写错用 [CORRECT] 追加更正行，不删改原记录
