# 模块生命周期流程树 + 签署责任矩阵 章节模板（模板 24）
> 🗂️ **产出模式**：多次创建-含文件夹（复制特化模板文件夹新建，如 specs/module-XXX/）；模板目录：templates/多次-含文件夹/（v10.0 目录规整）
> 📍 **变更记录方向**：新行插顶部（纯 AI 看；见 SKILL.md 文档维护规则第 9 条）

> ⚠️ **维护声明**：本文档修改后必须在末尾「变更记录」表追加一行——`YYYY-MM-DD HH:mm | 变更内容 | 署名`（署名按三元组 人-角色-实例，无法确认实例先问用户）。
> 模板用途：**每个模块全程运行**的「强制检查清单 + 流程导航」。产出物 = `memory/project/module-lifecycle-checklist.md`（仅 agent 操作、memory 本地不入 git；skill 初始化时随 CLAUDE.md D 区引用一起告知全员）；每模块从立项到收尾按本流程树逐阶段执行，防漏文档、防漏签署、防漏记忆库写入。
> 设计原则（决定能否跨技术栈复用）：**流程/纪律层=硬规则语言无关；命令/工具层=参数化占位（见第二部分三方向示例）；环境坑层=标注适用条件**。
> 配套纪律：签署责任矩阵防「创建者代签、后面 agent 忘记补签」；交接文档模板见 25-handoff-document.md；文档导航见 26-document-index.md。

## 第一部分：简化章节递归（结构一览）

```
模块生命周期（0 立项 → 6 收尾）
├── 阶段 0 模块立项          ← Planner：需求澄清→拆解→不变量→全量盘点→产 plan+acceptance
├── 阶段 1 开发前            ← 用户审批 plan → Developer 入场核对（读记忆库+git+plan 实测核对）
├── 阶段 2 开发完成收尾      ← Developer：自测+不变量自查+清临时文件→产 changelog→记忆库三文件+logs
├── 阶段 3 审查              ← Reviewer（独立 agent 禁自审）：产 review-report→不通过修复重审
├── 阶段 4 测试验收          ← Tester：单测回归+真实冒烟+种子核对→产 test-report+签署 acceptance→人工测试反馈闭环
├── 阶段 5 git commit/push   ← 用户明确允许 + 人工测试通过后才执行（memory/ 等惯例文件不提交）
└── 阶段 6 收尾回看          ← 工具/方法/踩坑归纳入记忆（时机=验收+文档+推送三者都完成）

签署责任矩阵（唯一出处见 CLAUDE.md C 区；本文件不再重复维护）
防遗忘三机制（唯一出处见 CLAUDE.md C 区）
中断恢复协议（RECOVERY：工作流被打断后先跑「恢复三问」，见本文件末尾章节）
```

## 第二部分：详细规格

### 各阶段「看什么 / 产什么 / 记忆库写什么」明细

**阶段 0 · 模块立项（Planner）**
- 看：`memory/project-context.md`（§5 迭代状态/§6 待办）→ `memory/file-index.md` → `docs/演进任务清单.md` + 需求来源（docs/ 功能说明 / 用户新需求 / 测试反馈）
- 做：需求澄清（ask 多轮问透、用户逐项拍板，**给出 2-3 种候选方案 + 优缺点**供用户拍板，选定后 **plan 只写入 1 种最终方案**，备选对比留设计文档/讨论记录）→ **复杂设计分章节产出、每章完成征得用户同意再继续**（简单设计可一次产出，复杂度是显式判断）→ 模块拆分（子任务七要素、默认 ≤200 行/模块）→ 定义不变量（编号列明）→ **全量实证盘点**（行号级，以代码为准）
- 产：`specs/module-XXX-<name>/plan.md` + `acceptance-criteria.md`
  - plan §8 审批记录 = 「Planner ✅ 已产出 / 待用户审批」状态；**acceptance 签署区禁止 Planner 填写，留空**
  - 两文件末尾变更记录各追加一行（`YYYY-MM-DD HH:mm | 内容 | 署名`）
- 记忆库：`agent-activity-log` `[PLAN]` 行 + project-context 状态→📋 待开发 + file-index 模块行 + `logs/planner/当日.md`
- 边界：需求定稿 = 上下文管理提醒点（压缩过/上下文紧张 → ask 是否开新会话，是→先写交接文档按模板 25）

**阶段 1 · 开发前（用户审批 → Developer 入场）**
- [用户] 看 plan + acceptance → 批复（同意/修改）→ Planner 落实修改 + 更新变更记录
- [Developer] 入场核对（强制，不看就动手=违规）：
  1. 读 `project-context.md` → `file-index.md` → `agent-activity-log.md` → `CLAUDE.md` → `memory/handoff/` 交接文档（如有，看完按 H4 处理）
  2. 跑 `git status` + `git diff --stat` 与 file-index 核对；未知变动先弄清来源
  3. 读本模块 plan + acceptance；**核对 plan §8 审批记录——若用户已口头批准但未回填 → 立即回填「用户/team-lead ✅ 已批准」行**（接手必核对第一动作）
  4. plan 与代码现状一致性核对（plan 会过时，行号级重验证）

**阶段 2 · 开发完成收尾（Developer）**
- 做：自测（命令见「三方向验证命令」）+ 不变量逐条自查 + 清理 `.tmp-xxx/`（方法先归纳进记忆再删）
- **开发中需求变更处理**：开发期用户提出需求变更/澄清/新要求 → ①判断「plan 内调整 vs plan 外新需求」②plan 内 → 与用户确认后更新 plan 变更记录，继续开发 ③plan 外 → 不擅自纳入本模块（plan 是唯一开发依据），记入下模块/需求池并告知用户 ④拿不准 → 问用户，不自行裁决
- 产：`changelog.md`（变更概述+文件变更列表+设计决策+自测结果+技术债务登记）；变更记录表追加本版行（Developer 署名）；**不代签 acceptance/review/test 任何签署区**
- 记忆库（阶段退出前置，缺一不可）：`agent-activity-log` `[CODE]` 行 + project-context 状态→👀 待审查 + file-index 新模块/入口文件行 + `logs/developer/当日.md`
- 交接：通知 Reviewer，附「已更新记忆库文件清单」
- 边界：进审查前 = 上下文管理提醒点（规范硬性边界）

**阶段 3 · 审查（Reviewer，独立 agent）**
- 看：plan（§0 审查要点 + §1 不变量）+ changelog + 记忆库三件套 + 代码 diff
- 操作：**用独立 subagent（`skill:review` 隔离审查），绝不 Developer 自审**（实测教训：自审判 PASS 漏 3 处 should-fix，独立 agent 一轮抓出）
- 核对项：权限码/种子完整性（对照设计文档逐条、搁置项不入种子）+ 不变量未破坏 + fail-closed（无权限→403）+ 前端隐藏≠安全（每个隐藏入口对应后端校验、直调 403）+ 缓存一致性 + SQL 注入/越权/编码正确性
- 产：`review-report.md`（结论先行 + 逐条核对 + 各轮记录 + 实测验证记录）；Reviewer 在结论/签署处署名
- 结果分两类退回：**实现缺陷**（代码 bug/不变量破坏/遗漏验收项）→ 退 Developer 逐条修复 → 重新独立审查；**需求偏差**（实现与用户真实意图不符，review-report 标记 `【需求偏差】`）→ **先回用户确认需求**（不许 Developer 自修、Reviewer 代答）→ 同步更新 plan/acceptance（需求基线变了，plan 是唯一开发依据）+ 变更记录 → Developer 按确认后需求修复 → 重新独立审查。直到 PASS（最多 3 轮）
- 记忆库：`agent-activity-log` `[REVIEW]` 行 + `logs/reviewer/当日.md` + project-context 状态→🧪 待测试

**阶段 4 · 测试验收（Tester，可带 Developer 协助）**
- 🔴 **硬规则：接口/环境冒烟 ≠ 浏览器人工测试**：①Tester 接口自测只代表服务端可用，不代表用户验收，禁止合并/顺带做 ②冒烟后不得宣称「测试已完成」；test-report 必须显式标注「浏览器人工测试未做，待用户实测」③只有用户按手册逐项实测并回报「通过」才算闭环，任何 agent 自测结论不能替代 ④未获「通过」前 commit 步骤保持 pending（联动防遗忘机制⑤）；冒烟记录无标注视为不完整，收尾四查①不通过
- ⚠️ **保留冒烟数据须标注对人工测试的影响（v10.12，ISSUE-006）**：若冒烟**保留**了测试数据（唯一键/查重/状态机/审批流等），必须在**人工测试手册模块节**「测试数据前置」标注「哪些保留数据需先清理或换新」，否则用户人工测试会撞业务前置（如「已存在双身份关联或申请」）——冒烟数据清理需用户确认（命令实测纪律），不静默清理
- 看：acceptance（§0 环境前置）+ review-report + changelog
- 核对：**acceptance 签署区状态——若已被创建者预填/代签 → 指出并要求按真实测试结果由 Tester 重签**
- 做：补单测 → 全量回归绿 → **真实环境冒烟**（含 DB/外部依赖的模块必须真实 DB 跑核心路径）→ 核对种子账号/数据（权限类改动种子够不够，不够就补+应用+冒烟验证）→ 人工测试手册按前模块样式更新 → **进度清单文档同步（逐项核对不许漏）**：①先判定模块所属工作线（五件套目录归属：`specs/`=主线，`<专项>-specs/`=专项）②同步该工作线的任务清单 checkbox + 模块状态表（仿名清单易混，按目录归属判定，不靠文件名猜）③同步全局文档导航索引 + 人工测试手册本模块节 ④每个文档变更记录区各追加一行；未完成项标注「延后」+原因
- 产：`test-report.md`（概览+覆盖率+验收逐条核对+失败详情含**环境性失败归因**+真实冒烟记录+清理记录）；**签署（核心动作，不允许跳过）**：test-report 结论/签署区 Tester 署名 + acceptance §签署区填「测试人=自己 + 结论 + 日期」（写完即填不留空）+ 任务清单 checkbox `[ ]`→`[✅]` + 变更记录区追加
- **人工测试反馈闭环（核心动作，用户实测后才允许 commit）**：
  1. **通知用户测试**：启动前后端 + 告知访问 URL / 种子账号密码 / 人工测试手册第几节 / 本模块临时数据改动说明——**不能「更新完手册就静默进入下一步」**（实测教训：不通知用户直接问 commit，用户才发现人工测试还没做）
  2. **显式等待用户反馈**：等用户按手册实测并回报结果，**不自动继续**；测试中若遇数据构成问题（如操作者数据范围内无测试目标）→ 先查库确认账号归属，无匹配时经用户确认临时绑定/补充，测后还原
  3. 用户反馈问题 → 逐条处理（修复 / 说明是设计行为 / 记入 test-report 备注）→ **请用户复测确认**；直到用户反馈「没问题」才算闭环
  4. 用户确认无问题 → 才允许进入阶段 5
- 记忆库：`agent-activity-log` `[TEST]`/`[REGRESSION]` 行 + `logs/tester/当日.md` + project-context 状态→✅ 已完成 + file-index
- 交接：通知 team-lead/Developer 可 commit（**前置 = 用户人工测试已通过**；commit 仍需用户明确允许）
**阶段 5 · git commit/push（前置：用户明确允许 + 人工测试通过 + 收尾四查；Developer/team-lead）**
- **commit 前置·收尾四查（强制 gate，四查未过不得 git add/commit）**：①签署齐全（acceptance/review-report/test-report/plan 审批，无代签漏签）+ **人工测试手册本模块节已产出**（v10.12：每模块验收必产该节，含步骤/账号/数据前置；模板 14 定格式，流程强制）②进度清单同步（按阶段 4 清单逐项核对，缺一项即停）③记忆库三文件 + logs 齐全 ④**测试数据状态**（冒烟/测试临时数据已清理恢复基线，或已明确告知用户保留并记录去向）
- **集成选项菜单（B4=多分支时，借鉴 finishing-a-development-branch）**：commit 前向用户展示并等待选择，不默认自动合并——
  1. 本地合并回基础分支
  2. 推送分支（可建 PR）
  3. 保留分支不动（用户稍后自己处理）
  集成方式**是用户的决定**（合并到错误基础分支代价很高，先确认分叉点）；用户未选前不执行合并/推送
- **合并后验证（B4=多分支时）**：若选择本地合并，**在合并结果上跑全量测试**再 push；合并结果失败 → 停下排查，分支与工作区原地保留（未推送前可恢复），不带着失败继续
- 做：`git add` 范围 = 代码/SQL/specs/docs；**不提交** memory/、.reasonix/、package*.json、步骤.md 等惯例文件；commit 信息 `[feat] module-XXX: 描述` → push 指定分支
- 记忆库：`agent-activity-log` `[COMMIT]` 行（记提交号+推送结果）；切分支轻量记一行；fetch/pull/stash 与纯读不记

**阶段 6 · 收尾回看（Developer/team-lead；时机=验收+文档+推送三者都完成）**
- 回看临时工具：跨模块可复用（≥2 场景）→ 固化 tools/（**删除演练**：删工具→项目照常编译）+ tools/README 登记复用记录
- 回看重要方法/模式（两阶段写入、批内释放编号、SQL 逐条执行+校验等）→ 记入 project-context 顶部或 reference 记忆
- 回看踩坑（编码/工具/框架行为）→ 并入已有 reference 或新增；跨项目通用 → 全局记忆
- 记忆库：logs 记一行检查记录 + `agent-activity-log` `[CONTEXT]`/`[DOCS]` 行；**无产出也要在 logs 记一行（防「忘了做」）**
- **成果审阅收口（必做）**：commit/push 后通知用户查看产出（URL/功能点/测试账号），显式邀请反馈——不默认「无反馈=无意见」；反馈分类落档：bug/小问题 → test-report 备注 + 排修复；改进/新需求 → 需求池（演进清单/专项清单对应条目）标注来源模块，不擅自纳入已完成模块
- **下一步对齐（阶段 6 收尾最后一步）**：主动问用户「下一个模块做哪个」（按清单顺序 or 用户指定），不默认自动开；用户暂停 → 记录暂停点（project-context 状态 + 待办），不擅自开工

### 签署责任矩阵与防遗忘三机制（唯一出处见 CLAUDE.md C 区）

> 签署责任矩阵（谁验收谁签署/签署时点/接手核对动作）与防遗忘三机制（禁止代签/接手必核对/签署即完成）**完整表定义在 CLAUDE.md C 区**，本文件不重复维护——避免双份漂移。生成 CLAUDE.md 时自动带上；本文件只需在阶段入口核对「前序文档签署状态」（见各阶段明细）。

### 中断恢复协议（RECOVERY）— 工作流被打断后的回归程序

> 适用：开发中工作流被意外打断（**无交接文档的强杀/闪退/断网、agents 上下文丢失或压缩后失真、软件直接退出**），恢复后 agents 不得凭印象继续，必须先执行本协议定位「我在哪一步、该做什么、有什么没做完」，否则极易脱离固定流程（阶段遗漏/重复/跳跃）。
> 依据：记忆库三文件（project-context 状态 / agent-activity-log 最近行 / file-index）+ `memory/handoff/` 交接文档 + 任务清单 checkbox + specs 各文档签署状态 + `git status`。记忆库是恢复的唯一权威依据（不臆测、不凭记忆断言）。

**R1 · 恢复三问（任何阶段中断恢复后的强制第一步）**
1. **我在哪一阶段？** → 看 `project-context.md`（模块状态：📋/🔧/👀/🧪/✅）+ `agent-activity-log.md`（最近一行是什么动作）+ 任务清单 checkbox 勾到哪 → 得出「当前阶段 + 该阶段做到第几项」
2. **该做什么？** → 读本阶段 checklist 明细（阶段 0-6）+ specs 本模块文档签署状态（谁签了、谁没签）→ 确定下一未完成动作
3. **有什么没做完/做了一半？** → `git status`/`git diff --stat` 核对工作区（未提交改动=开发中产物，**不要擅自丢弃或提交**；丢弃半成品必须用户**精确确认**——如回复指定确认语，不默认清理，借鉴 finishing「输入 discard 才授权删除」）+ `memory/handoff/` 是否有交接文档（有→读完删；无→按 R2 重建）+ 临时数据改动是否已还原（数据库基线）

**R2 · 交接文档缺失时如何重建进度**
- 无交接文档 ≠ 进度丢失：按顺序拼出当前进度——
  1. `project-context.md` 模块状态与最近更新摘要（谁在何时做到什么）
  2. `agent-activity-log.md` 该模块最近 2-3 行（PLAN/CODE/REVIEW/TEST 做到哪一环）
  3. specs 五件套签署状态（plan 审批/acceptance/review/test 谁已签、谁欠签）+ 任务清单 checkbox
  4. `git status` 工作区改动（半成品代码即「开发中」证据，diff 内容可反推做到哪一步）
- 拼完后：上下文允许 → 按交接文档规范（模板 25）**补写交接文档**；上下文已紧张 → 建议用户开新会话，并在提醒中说明已按 R2 重建的进度

**R3 · 上下文丢失/压缩失真时的处理**
- 一旦发现「对当前模块进度凭印象、拿不准细节」→ **立即停手**，重读记忆库三文件 + 本流程文件 + 本模块 specs；禁止凭记忆继续写代码/签署
- 上下文已压缩 ≥1 次 → 主动提醒用户开新会话（是→旧会话按 R2 补交接文档；否→说明持续压缩坏处）
- 压缩后无法确定「已做未做」的事项 → 以记忆库/签署状态/git 为准，拿不准的宁可重新验证（跑测试/查库）也不臆测

**R4 · 各阶段入口的恢复引用**
| 阶段 | 入口动作 | 中断恢复引用 |
|------|----------|--------------|
| 阶段 1 开发前 | 入场核对（读记忆库+git+plan+审批记录回填） | 已覆盖恢复三问第 1/2 问；中断场景 → 同列动作重跑一遍 |
| 阶段 2 开发收尾 | 自测+不变量自查 | 入口补「R1」：确认 T1-Tn 做到哪、changelog 是否已产、`.tmp-xxx/` 是否有残留 |
| 阶段 3 审查 | 独立审查 | 入口补「R1」：确认 review-report 是否已产、结论 PASS/FAIL、Developer 是否已修复 |
| 阶段 4 测试验收 | 核对 acceptance 签署区 | 入口补「R1」：确认 test-report/acceptance/手册做到哪、**人工测试闭环是否完成** |
| 阶段 5 git | 用户允许 + 前置检查 | 入口补「R1」：确认阶段 4 人工测试已通过 + 用户允许（两前置缺一不可） |
| 阶段 6 收尾回看 | 工具/方法/踩坑归纳 | 入口补「R1」：确认验收+文档+推送三者是否都完成（时机判定） |
