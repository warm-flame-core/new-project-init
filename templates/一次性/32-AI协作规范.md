## 第二部分：详细规格（写什么 / 格式 / 示例）

> **写什么**：本文件承载**只给 agent 看的行为门禁**（记忆纪律 + 签署责任 + 防遗忘），不追求文档排版美感，追求**无歧义、可判定、无借口空间**。人可读，但第一受众是每次入场都要执行的 agent。
> **生成时**：① 表格与条目**逐项搬齐**，不因「项目简单」删条（简单项目只影响签署矩阵里不产出的文档行，删除该行即可）② 项目特有事实（如具体角色名映射、具体文档名）可在表格旁补充，但不改写门禁措辞。

### 1. 记忆库纪律

- **写什么**：agent 每轮答完前必须自问的三件事 + 触发条件清单 + 标签词表 + 借口拦截表。**这是「忘写记忆库」的唯一防线**，逐条照搬。
- **触发（任一必须写）**：开发改文件 / 测试（记结果数字）/ 审查（结论+遗留）/ git 实质操作（commit/push/merge/reset 记提交号；切分支轻量一行；fetch/pull/stash 与纯读不记）。
- **末尾自检四步（v11.4：与 SKILL.md 记忆库写入纪律第 2 条对齐；比原「三步」多一步动作回看）**：①本轮动了哪些文件 ②记忆库是否已覆盖（project-context 更新日志 / file-index 新行 / activity-log 活动行 / logs 细档）③**动作回看**——本轮是否发生了 `<入口规范文件>`「**动作 → 必须更新**」表里的任一动作（新增/删除 工具·脚本·命令、新增外部依赖、改环境要求、**新增/改 构建·测试·运行命令**、增改 接口·路由·权限点、增改 表·字段、增删目录·移动文件、踩到新坑并解决、引入新的第三方约定；**此处枚举只是提醒，判据以整表为准**）？**逐条对照，对应文档没更新不许结束** ④缺则补写。
- **入场核对（强制）**：读 project-context → file-index → activity-log → `<入口规范文件>` → handoff/（如有，看完删）；跑 git status + git diff --stat 与 file-index 核对，未知变动先弄清来源。
- **临时文件纪律**：临时脚本放 .tmp-xxx/（不入 git），用完即删，用法记 logs。
- **动作标签表（唯一出处，logs 细档与 activity-log 均用此表）**：

| 标签 | 语义 |
|------|------|
| PLAN | Planner 产出 plan/acceptance |
| CLARIFY | 需求澄清（ask 问询） |
| CODE | 编码实现 |
| FIX | 修复（审查/测试退回后） |
| BUILD | 构建/编译验证 |
| REVIEW | 独立审查产出 review-report |
| ADR | 架构决策记录 |
| TEST | 测试/验收 |
| REGRESSION | 回归测试 |
| SMOKE | 真实环境冒烟 |
| BLOCKED / UNBLOCKED | 阻塞 / 解除阻塞 |
| HANDOFF | 交接（交接文档产出/删除） |
| CONTEXT | 上下文管理（提醒开新会话等） |
| CORRECT | 更正（logs 历史纠错，追加不删改） |
| ESCALATE | 重试上限升级申请 |
| GIT | git 实质操作（commit/push 记提交号） |
| DB | 数据库操作（迁移/查证/清理） |
| CLEANUP | 环境/临时文件清理 |
| DOCS | 文档产出/修订 |

> 计数口径：上表 **19 行、20 个标签**（BLOCKED 与 UNBLOCKED 共用一行）——其他文档写「动作标签 20 个」即按此计数；引用方**只引用不复制本表**。
- **借口自查表（记忆纪律）**：

| 借口 | 现实 |
|------|------|
| 「就改一行代码，不用记」 | 一行改动也是开发动作，触发条件满足任一就必须写 |
| 「测试通过了不用记结果」 | 无论成败都要记结果与数字，失败记录更值钱 |
| 「我下次会话再补」 | 换会话就丢了，动作即写 + 末尾兜底 |
| 「这次是纯读没动文件」 | 纯读确实不记；动了文件/跑了测试/审查了就必须记 |

**红线**：以上借口出现任何一个 → 停下补写记忆库再继续。

### 2. 签署责任矩阵（★ 本表为签署责任矩阵唯一出处）

- **写什么**：六类协作文档的「谁创建 / 谁签署 / 签署时点 / 接手核对动作」——防代签、漏签，让「谁负责什么」可追查。
- ⭐ **唯一出处声明（必写，显著位置）**：**本表为签署责任矩阵唯一出处**。引用方（`memory/project/module-lifecycle-checklist.md`（模板 24）/ agents 角色文件（模板 06）/ specs 五件套签署区（模板 17-21）/ 交接文档（模板 25））**只写「见 `<AI协作规范文件>`」，不复制表格**；改矩阵只改本表，改完检查引用方无漂移。
- **入口文件的摘要行**：`<入口规范文件>` 的签署矩阵摘要行**指向本文件，不复制表格**（详见 §4）。

| 文档 | 创建者 | 谁签署 | 签署时点 | 接手核对动作 |
|------|--------|--------|----------|--------------|
| plan.md | Planner | Planner 维护状态 + 用户/team-lead 审批 | 立项末→用户批复 | Developer 入场看审批记录，已批未回填立即回填 |
| acceptance | Planner | **只有 Tester** | 测试验收后 | Tester 接手第一步核对签署区留空/被代签 |
| changelog | Developer | Developer（每版追加） | 开发完成 | Reviewer 核对自测与代码一致 |
| review-report | Reviewer | Reviewer | 审查完成 | Tester 看结论是否 PASS |
| test-report | Tester | Tester | 测试完成 | team-lead/Developer 收尾核对 |
| 人工测试手册 | Tester | 无签署但必更新 + 用户实测 | 测试完成→用户确认 | 下模块参照样式 |

> 📌 **「追加 vs 更新」区分（v10.0，防无脑追加）**：签署/变更记录前先判断该文件类型——
> - **追加式（memory/ 三件套 + logs + 变更记录表）**：只在末尾追加新行/新表项，**不改旧内容**。
> - **更新式（docs/、specs/ 正文、agents/）**：改内容 + 末尾变更记录追加一行 + 署名；**正文不可只追加不更新**（内容与变更记录必须同步）。
> - **签署必带日期**：签署区/变更记录日期 = 实际签署当天（系统日期为准），禁止沿用旧日期或预写未来日期；写错用 [CORRECT] 追加更正，不删改原记录。

- **示例片段（`<入口规范文件>` 里保留的摘要行，只此三行、无表格）**：

```markdown
## 签署责任矩阵（摘要）

- 一句话纪律：创建者只签自己的区、禁代签；接手先核对前序签署；acceptance 只有 Tester 签。

```

### 3. 防遗忘机制 + 收尾四查

- **写什么**：防止「签字/核对/收尾」被顺手跳过的硬 gate——**防遗忘机制**（5 条，本文件列全）+ **收尾四查**（commit 前置，只列标题、明细指向模板 24 阶段 5）。
- **防遗忘机制（5 条）**：
  ①禁止代签（创建者只签自己的区）
  ②接手必核对（每阶段入口核对前序签署）
  ③签署即完成（没跑冒烟不许签 acceptance、没独立审查不许签 review-report）
  ④**commit 前置 = 用户人工测试通过**（未获用户按手册实测并回报「通过」前，不允许 git commit；阶段 5 同步保留此前置，两处修改须同步防漂移）
  ⑤**todo 强制 gate**（「人工测试反馈闭环」「收尾四查」必须拆成独立阻塞步骤，不允许揉进其他步骤顺带做，靠一步一签核卡住；**接口冒烟 ≠ 人工测试**——Tester 自测通过 ≠ 用户实测通过，未获「通过」反馈前 commit 步骤保持 pending）。
- **计数口径**：统一写「防遗忘机制（5 条）」，**不写「三机制 / 五机制」**（历史口径冲突点，见头部计数口径声明）。
- **收尾四查（commit 前置 gate）**：①签署齐全 + 人工测试手册本模块节已产出 ②进度清单同步 ③记忆库三文件 + logs 齐全 ④测试数据状态——**四查明细唯一出处 = 模板 24 阶段 5**（本文件只列标题，不复制明细，避免双份漂移）。
- **示例片段（收尾四查落成 todo 阻塞步骤，照此拆，不许揉进其他步骤）**：

```markdown
- [ ] 收尾四查①：签署齐全（无代签漏签）+ 人工测试手册本模块节已产出
- [ ] 收尾四查②：进度清单同步（任务清单 / 模块状态表 / 导航索引逐项核对）
- [ ] 收尾四查③：记忆库三文件 + logs 齐全（含各角色 logs）
- [ ] 收尾四查④：测试数据状态（临时数据已清理恢复基线，或已告知用户保留并记录去向）
- [ ] 用户按手册逐项实测并回报「通过」  ← 未打勾前 commit 步骤保持 pending
```
