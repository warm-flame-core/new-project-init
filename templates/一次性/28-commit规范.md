# Commit 提交规范 章节模板（模板 28）
> 🗂️ **产出模式**：一次性文档；模板目录：templates/一次性/（v11.0 新增，源自 ISSUE-011）
> 📍 **变更记录方向**：新行追加底部（有人看；见 SKILL.md 文档维护规则第 9 条）
> 🧩 **装配方式**：可选规范模块（见 SKILL.md「规范装配问询」）——问询时问用户「有没有自己的 commit 规范」
>   - **有自定义规范** → 特化时**结合用户规则优化本模板**，并在特化文件开始前**告诉用户优化结果**
>   - **无自定义 + 内容按量裁决**：内容多（可提炼成多行规范）→ 产出本独立文件（如 `docs/commit规范.md`）；内容少（仅小建议）→ 并入 `<入口规范文件>` 协作相关章节
>   - 「不需要」→ 不生成（沿用模板 24 阶段5 的 commit 前置纪律）
> 📎 **参考来源**：本模板对 superpowers-zh `chinese-commit-conventions` 的中文版提炼（Conventional Commits 类型表/格式）。

> ⚠️ **维护声明**：本文档修改后必须在末尾「变更记录」表追加一行——`YYYY-MM-DD HH:mm | 变更内容 | 署名`（署名按四段式 实体人-平台-角色@分支（无 git 省略 @分支，如 warmflame-Reasonix-Developer@feat/xxx）；无法确认身份先问用户）。

## 第一部分：章节结构一览

```
Commit 提交规范
├── 提交信息格式（Conventional Commits 中文版）
├── 类型清单
├── 好的 / 不好的 commit message 示例
├── 分支命名规范（feat/fix/hotfix/release 全小写连字符）
└── 合并规范（rebase / 冲突处理 / 合并后验证）
```

## 第二部分：详细规格（写什么 / 格式 / 示例）

### 1. 提交信息格式（Conventional Commits 中文版）

```
<类型>(<范围>): <中文简要描述>
               ← 空行
<正文（可选）：动机 / 方案 / 影响>
               ← 空行
<脚注（可选）>
```

- `<类型>`：见下方类型清单；`<范围>`：模块/文件/子系统名（可选，能看出改动归属）。
- `<中文简要描述>`：一句话，说清"做了什么、解决什么"，不笼统（拒绝「update code」「fix bug」）。
- 正文写**动机 / 方案 / 影响**三要素；涉及 Bug/需求可加 `关联需求：TAPD-12345`、`Closes #567`。

### 2. 类型清单

| 类型 | 说明 |
|------|------|
| `feat` | 新增功能 |
| `fix` | 修复 Bug |
| `docs` | 文档更新 |
| `style` | 代码格式（不影响逻辑） |
| `refactor` | 重构（不是新功能也不是修 Bug） |
| `perf` | 性能优化 |
| `test` | 测试相关 |
| `build` | 构建系统或外部依赖 |
| `ci` | CI/CD 配置 |
| `chore` | 其他杂项 |
| `revert` | 回滚 |

### 3. 好的 / 不好的示例

**好 **：
```
feat(购物车): 支持批量删除商品

- 新增全选/反选功能
- 删除操作增加二次确认弹窗
- 批量删除接口使用 POST /cart/batch-delete

关联需求：TAPD-12345
```
```
fix(支付): 修复微信支付在 iOS 16 上无法唤起的问题

原因：微信 SDK 8.0.33 在 iOS 16 上 Universal Links 校验逻辑变更。
方案：升级 SDK 至 8.0.38，更新 Associated Domains 配置。

Closes #567
```

**不好**：`update code`、`fix bug`、`fix: 修复问题`（无上下文）、`fix：修复了一个bug，因为user login的时候会crash`（中英混杂无规范）。

### 4. 分支命名规范（团队可 on/off）

- 全部小写，用 `-` 连接（不用下划线或驼峰）。
- 前缀明确类型：`feat/`、`fix/`、`hotfix/`、`release/`；可关联任务编号：`feat/TAPD-12345-order-refund`。
- 长度适中、能看出分支目的。

### 5. 合并规范

- **合并前先 rebase 到最新 main**：`git fetch origin && git rebase origin/main`，解决冲突后再合并。
- **冲突处理**：只保留对方为准 + 本地必要的部分，逐文件确认，不静默丢弃任一方。
- **合并后验证**：在合并结果上跑全量测试再 push；合并失败 → 停下排查，分支与工作区原地保留（未推送前可恢复）。
- 集成方式（合并回基础分支 / 推分支建 PR / 保留分支）是**用户的决定**，不默认自动合并（见模板 24 阶段5 集成选项菜单）。
