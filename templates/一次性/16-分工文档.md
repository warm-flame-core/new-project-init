# docs/分工文档.md 章节模板（模板 16）
> 🗂️ **产出模式**：一次性文档（skill 特化即正式文件，后续修改=更新式：改内容+变更记录+署名）；模板目录：templates/一次性/（v10.0 目录规整）
> 📍 **变更记录方向**：新行追加底部（有人看；见 SKILL.md 文档维护规则第 9 条）

> ⚠️ **维护声明**：本文档修改后必须在末尾「变更记录」表追加一行——`YYYY-MM-DD HH:mm | 变更内容 | 署名`（署名按四段式 实体人-平台-角色@分支（无 git 省略 @分支，如 warmflame-Reasonix-Developer@feat/xxx）；无法确认身份先问用户）。
> **一次性文档**（多人协作时产出，F1/E1 选「分工」）。示例写在开头，agents 按问询答案追加/替换填写。
> 定位：多人开发时谁做哪个模块、怎么并行不打架、怎么合并。

## 第一部分：章节结构一览

```
docs/分工文档.md
├── # <项目名> - 后端/全栈功能模块分工文档
├── ## 一、模块总览       ← 模块清单 + 负责人
├── ## 二、模块依赖关系   ← 谁依赖谁（决定开发顺序）
├── ## 三、各模块详细分工 ← 每模块：负责人/接口/数据库影响
├── ## 四、分工方案建议   ← 按人分配建议（能力/工作量平衡）
├── ## 五、开发阶段规划   ← 阶段 → 并行模块 → 里程碑
├── ## 六、模块间联调清单 ← 接口联调点 + 契约
├── ## 七、接口文档维护   ← 谁更新接口文档
├── ## 八、代码合并规范   ← 分支策略/合并顺序/冲突处理（B4）
└── ## 九、风险与依赖     ← 阻塞风险/共享表冲突
```

## 第二部分：详细规格 + 示例

- **一、模块总览**：`模块 | 负责人 | 状态` 表。
- **二、模块依赖关系**：A 依赖 B（先做 B），共享表/共享 Service 标注。
- **三、详细分工**：每模块写明负责人、涉及接口、**数据库影响**（谁建表谁迁移，迁移号分配规则 U4——避免撞号）。
- **四、分工方案建议**：按人给出建议分配与理由（工作量/技术点匹配）。
- **五、开发阶段规划**：阶段表 `阶段 | 模块 | 并行说明 | 里程碑`。
- **六、联调清单**：接口契约（入参/出参/错误码）由谁定、谁先出 stub。
- **七、接口文档维护**：接口文档更新责任人与更新时机（每模块完成即更新）。
- **八、代码合并规范**：分支策略、合并顺序（避免共享文件冲突）、冲突解决归属（B4/B7）。
- **九、风险**：共享表并发改（迁移号撞号）、接口契约变更未同步等。

### 示例（结构示范）
```markdown
# 高校企业对接管理平台 - 后端功能模块分工文档

## 一、模块总览
| 模块 | 负责人 | 状态 |
|------|--------|------|
| 资质审核 | 张三 | ✅ |
| 培训班 | 李四 | 📋 |

## 二、模块依赖关系
培训班依赖资质审核（机构需审核通过才能发班）；先完成审核模块。

## 三、各模块详细分工
### 资质审核（张三）
- 接口：/api/qualification-audit/**
- 数据库：qualification_material 字段（迁移号 V2，张三分配）

## 五、开发阶段规划
| 阶段 | 模块 | 说明 |
|------|------|------|
| 1 | 资质审核 | 地基先行 |
| 2 | 培训班 + 学生管理 | 可并行（不同表） |

## 八、代码合并规范
- 分支：feature/module-XXX → develop；共享文件（schema.sql）改前先拉最新，避免冲突。
- **合并规范（ISSUE-011，完整见模板 28-commit规范.md）**：合并前先 rebase 最新 main（`git fetch && git rebase origin/main`）并解决冲突；冲突处理只保留对方为准 + 本地必要部分，逐文件确认不静默丢弃任一方；**合并后在合并结果上跑全量测试再 push**；集成方式（合并回基础分支/推分支建 PR/保留分支）是用户的决定，不默认自动合并。
```
