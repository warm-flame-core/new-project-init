# 五件套颗粒度标尺 · 写作前必读（reference 文件，v11.3，ISSUE-019）

> 🗂️ **定位**：写 / 审 / 改 **specs 五件套**（plan / acceptance / changelog / review-report / test-report）前**必须读完本文件全文**——它回答模板骨架回答不了的问题：「每节要写到多细、一格要填多少、什么叫做简略了」。
> 🔒 **加载保证（跨平台强门禁）**：本文件与 `references/场景/*.md` 同级受「跨平台强门禁」约束——写五件套前未读全文 = 违规（Reasonix auto-fold 也要按规则确认已读；DSH/ZCode/其他平台靠 SKILL.md 硬门禁强制去读）。子代理由 `agents/<role>.md` 的 references 必读行保底（见 SKILL.md「跨平台强门禁·覆盖范围与兜底」）。
> 📍 **变更记录方向**：本文件自身不设独立变更记录表；改动随 SKILL.md 版本表 + `docs/CREATION-LOG.md` 同步（与 references/场景/ 三题库同一约定）。

## 为什么需要标尺（根因一句话）

模板给的是**结构骨架**（章节 + 格式），骨架对齐 ≠ 颗粒度对齐——agent 看着模板仍会写简略，因为「详细」没法凭想象编出来。五件套的颗粒度来自**证据密度**：每一段都是实测证据（`文件:行号`、grep 计数、DDL 引用、验收项逐条核对），**证据写满了，详细是副产品**。所以本标尺的用法不是「写长一点」，而是：

1. **先盘点后写作**：动笔前把 §3.1 盘点 / 不变量 / BDD 场景逐项实测出来（grep/read/跑命令），没证据的行不许写；
2. **按下限表自检**：写完对照下方「颗粒度下限表」逐项核对，缺项 = 返工；
3. **有样板对标样板**：项目 `specs/_样板/` 已固化的，先读样板全文再写，收尾与样板逐节比对（机制见 SKILL.md「探索与产出」第 3 条，唯一出处不在此重复）。

## 颗粒度下限表（中档，可核对）

> **下限是底不是目标**：复杂模块（多链路 / 多子任务 / 动存量核心）按下表**上浮**（样板 module-018 实际为：不变量 13 条、BDD 10 场景、验收 A 组 12 + B 组 6 + C 组 6 项）。简单模块走结构 B 时**证据密度要求不降**（每条事实仍须实测锚），下限项可在 §0/变更记录显式说明后按比例缩减（说明理由即可，不许默默跳过）。

## BDD 场景类型覆盖清单（v11.3，ISSUE-025）

plan §1 的 BDD 场景**不是随手列几个主流程**——按下列类型逐类检查，`≥5 个场景` 时应覆盖到每一类（某类确实不适用可跳过，但须在场景清单后注明「无 XX 场景，因…」）：

1. **主流程**：用户核心操作路径（做成了会怎样）；
2. **边界与非法输入**：空值 / 超限 / 重复 / 格式错；
3. **权限失败**：越权访问（他人/其他角色）+ 匿名未认证；
4. **已有数据 → 修改 → 重传**（批量修改流，ISSUE-025 教训：只写「新建→上传」漏掉「已有数据怎么改」，用户实测才发现需求缺口）——凡模块涉及「下载模板 / 导入导出 / 批量操作」，必须补「已有数据 → 导出/下载 → 修改 → 重传/覆盖」场景；
5. **降级 / 回滚 / 失败补偿**：依赖不可用、部分失败、整批回滚。

> 问询期追问一句（模板 24 阶段 0 落地）：「用户实际操作的**完整**流程是什么？包括在已有数据上修改的场景」——把修改流在 plan 阶段挖出来，不要等测试阶段临时加功能。

## 硬验收加粗词表（30 个，跨技术栈替换）

> 五件套的**加粗硬验收措辞**是样板颗粒度的浓缩信号（审查要点 / 不变量 / 验收组都靠它们锚定）。下表分类给出：**通用直接复用** + **按技术栈替换关键词**（结构与语义不变，只换词）。未细化的技术栈用保底格式：`**[技术栈] 配置零改动**` 并在语义上对齐同类型。
